### 2. 技术选型
-
- **后端框架选择及理由**：选择 Java 17 + Spring Boot。本项目核心业务涉及严格的“积分划转”与“违约扣除”，Java 的强类型系统和 Spring 生态的成熟度非常适合处理这种严谨的业务逻辑；同时 Spring Security 能方便地实现学生端与教师管理端的角色权限隔离。
- **数据库选择及理由**：选择 MySQL 8.0。积分互助系统包含明确的实体关系（用户-发布委托-接单-产生积分流水），属于典型的关系型数据模型。我们需要利用 MySQL 的事务（ACID 特性）来保证悬赏发布和积分扣除时的数据强一致性，防止“超卖”或积分异常。

## 遇到的问题和解决
1. **问题**: 在设计“学生接单”和“积分划转”流程时，发现如果有多人同时点击“接单”，可能会导致同一个任务被多人接取，或者积分结算出现并发冲突。
   **解决**: 在数据库设计时明确了基于状态机（0-待审,1-待接,2-进行中,3-完成）的流转逻辑，并在架构设计文档的交互流程中明确规定：后端在处理接单请求时，必须使用数据库事务，并利用 MySQL 的条件更新（例如 `UPDATE tasks SET status = 2 WHERE id = ? AND status = 1`）来防止并发冲突，保证积分交易的安全。

## 心得体会
在这次架构设计作业中，我深刻体会到了“谋定而后动”以及规范化文档的重要性。通过使用 Mermaid 绘制前后端架构图和系统交互流程图，将原本模糊的“学生接单与积分变动”业务梳理得非常清晰。这也让我意识到，在真正动手写代码之前，先确定好前后端的职责边界、API 规范以及数据库表结构，能够大幅降低后续团队协作时的沟通成本和返工率。
